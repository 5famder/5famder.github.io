Git Commit Message Generator

feat(learning): teach juniors to write, check and fix commit messages

AudienceJunior developers, 0–2 years
Duration4 minutes, 6 screens
FormatNarrated, interactive, built in Storyline 360
PrerequisiteAlready uses Git and makes commits
Learning objective

After this lesson, a junior developer can generate a commit message with Git Commit Message Generator, check it against the Conventional Commits format, and correct it before committing.

Left out on purpose: message body and footers, breaking changes (!), squashing and rewriting history, setting up commitlint. Each is worth its own lesson, and none of them is needed to meet the objective above.

Approach

Merrill's First Principles, scaled down to four minutes.

I built the lesson on Merrill's First Principles, scaled down to four minutes. It opens with a situation juniors already know, a broken release and a log full of "wip" and "fix", so the format arrives as the answer to something they have just struggled with. The learner is doing something for 2 minutes 20 seconds out of 4, and support fades as they go: first they recognise a good message, then choose between three, then fix one on their own. I present the tool as something that writes the first draft, because the habit I want juniors to leave with is reading a suggestion before accepting it. For the same reason the product is named only twice, in the demo and at the end, since a lesson that sells on every screen stops being trusted.

Why this format

Written storyboard with key frames.

The lesson is narrated, so the script carries most of the meaning, and a script is what a reviewer can check line by line. Every screen below uses the same rows in the same order: narration, on screen, learner action, feedback, technical notes. I only mocked up the parts where layout is part of the learning, like the commit log, the IDE and the message segments. The mockups are kept plain on purpose, so review stays on the content and not on colours.

The script has already been read by working developers, who checked the Git content for accuracy and clarity (see Technical review below). The next step would be a clickable prototype of screen 5 in Storyline, tested with two or three junior developers before the full build.

Narration
"You're on call this week. Since Tuesday's release, customers can't pay. Six commits went out that day. Find the one that broke checkout."
On screen
Red incident banner fades in first, then the six commits appear under it (State 1). After the first click, the same list swaps to clear messages (State 2).
Learner action
State 1: clicks any commit. State 2: clicks the commit that caused the bug.
Feedback
  • State 1, any click: "You couldn't have known. Neither could whoever wrote these. And honestly, that was probably you, three weeks ago."
  • State 2, narration: "Same commits, same code. Only the messages changed. Try again."
  • State 2, correct (2d47a19): "Found it in two seconds. Nothing about the code changed. Only the messages did."
  • State 2, wrong: "Not that one. Look for the commit that touches checkout."
Technical notes
One slide, two states. Banner appears 1 s before the list. In State 1 every commit is a hotspot and any click opens the feedback layer, then State 2 loads when narration ends. In State 2, unlimited attempts. After the second wrong click, 2d47a19 gets a soft highlight. Next unlocks only after the correct click.

SCREEN 4

Choose the best message

40 sGuided practice
cart.js
- const maxItems = 10;
+ const maxItems = 20;

Same change, three messages. Which one would you commit?

A
fix(cart): update maxItems

Feedback"Two things. Nothing was broken, a limit went up, so it's a feat and not a fix. And 'update maxItems' names the variable instead of saying what changed for the customer."

B
feat(cart): allow up to 20 items per order

Correct"Yes. Right type, clear scope, and the description tells you what customers can do now."

C
feat: change the maxItems constant in cart.js from 10 to 20 as agreed with product

Feedback"Right type, but no scope, and it describes the line you edited. The part about product belongs in the message body or the pull request."

Narration
"Here's a small change and three ways to describe it. Pick the one you'd want to find in the log a year from now."
On screen
Diff at the top, three options as cards below, Submit button.
Learner action
Selects one option and clicks Submit.
Feedback
Per option, shown above. After the correct answer, narration: "All three describe the same edit. Only one still makes sense next year."
Technical notes
Single-select, options shuffled. Two attempts. After the second wrong answer, B is highlighted with its explanation. Next unlocks after the correct answer is shown. Wording does not claim the tool offers several drafts, so the screen works whatever the tool's UI does.
SCREEN 5

Fix the draft

60 sIndependent practice
auth/login.js
+ <input type="checkbox" id="remember-me" />
+ if (rememberMe) setSessionDuration(30 * DAY);

This draft needs one change before you commit. Click the part that's off.

Start state · all parts look the same

fix(auth): let users stay signed in for 30 days

After step 2 · corrected

feat(auth): let users stay signed in for 30 days
Narration
"Your turn. This change adds a 'remember me' box to the login page. Here's the draft. One part needs changing before you commit. Find it."
On screen
Diff at the top. Draft message below, split into three clickable parts, all in the same neutral style so nothing gives the answer away. Step 2 appears under the message once the right part is found.
Learner action
Step 1: clicks the part that's wrong. Step 2: picks the right type from feat · refactor · chore.
Feedback
  • Clicks scope: "The scope is fine. This change lives in authentication. Look again."
  • Clicks description: "The description works. It says what users can do now. Look again."
  • Clicks type: "That's it. Nothing was broken here. So what kind of change is it?"
  • Picks feat: "Right. It's a new capability. Final message: feat(auth): let users stay signed in for 30 days."
  • Picks refactor: "A refactor changes how code is organised but not what it does. Here users get something new."
  • Picks chore: "Chores are maintenance users never notice. They'll notice this one."
Technical notes
Step 1: three labelled buttons ("type: fix", "scope: auth", "description"), unlimited attempts, each wrong click shows its hint layer. Correct click marks the type in red with the label "needs a change" and reveals step 2. Step 2: two attempts, then feat is shown with the explanation. The word swaps in place in the message. Closing narration after success: "Nothing was broken, so it isn't a fix. That's the check to make every time." Next unlocks after that line.

Questions for the product team

What I assumed, and what I'd confirm before building.

  1. Where is the Generate button? Screen 3 uses an icon inside the VS Code message field as a placeholder. I'd need the real name and position in VS Code, IntelliJ and the web app.
  2. One draft or several? Screen 4 is worded so it works either way, but the demo narration should match what the tool really does.
  3. Can it learn a project's own scopes, for example from a commitlint config? If yes, the scope fix in screen 3 turns into a one-line setup tip, which is a nicer story for the product.
  4. Which links and tracking should the last screen use?
Accessibility

Colour never carries meaning on its own. Segments on screens 2 and 5 have numbers or text labels too, and the warning on the limit card has an icon and a heading. Everything clickable is a real button that works by keyboard, in reading order. Narration is captioned, and the lesson works with the sound off, because each narrated point also shows up on screen as a keyword or a code sample. Code is live text, not images, so screen readers can read it and it scales without blurring.

Production and evaluation

Built in Storyline 360 rather than Rise, because screens 1 and 5 need state changes and a two-step interaction that Rise blocks can't handle cleanly. Estimate: 6 to 8 hours plus narration recording. Screen 3 is the only custom animation, made from the Figma frames in the VS Code Dark+ palette. To see whether it worked, I'd look at first-try accuracy on screen 5 and at how many learners click an install button.
