How I design

This is how I worked on all three projects. I start by using the product myself and finish by checking that the course actually works.

1

Use the product as a beginner

I go through onboarding myself and write down every place I get stuck.

Found: the quickstart model was Dedicated-only, so new users' first call failed.

2

Define the learner and the gap

One sentence on who they are, what they can already do, and what they get wrong today.

"Knows Python and the terminal, has never called an LLM through an API."

3

Write objectives backwards

What the learner can do at the end, as observable actions. Then the assessment. Then the content.

Create a key · send a request · read the response · change it.

4

Choose the model for the skill

A procedure, a judgement skill and a habit need different designs. I pick the model to match.

Prompting is a judgement skill, so AI Prompting Essentials uses 4C/ID.

5

Blueprint before the tool

Every lesson gets one goal and one learner action on a single page before I open Rise.

A lesson with no action of its own gets merged.

6

Use real data only

Model names from the live catalog, code I ran, outputs I generated. No invented examples.

11 real ChatGPT outputs power the "Fix the prompt" interaction.

7

Build with the right tool per job

Video for the "why", click-through demos for the "how", interaction for practice.

HeyGen · Supademo · Figma · Rise · custom HTML.

8

Test accessibility and tracking

Captions, keyboard use, colour never alone, mobile. Then an LMS test run.

SCORM Cloud: complete, passed, 75%.

9

Review with an expert and learners

An engineer checks technical accuracy; a small pilot shows where learners struggle.

Feedback that isn't confirmed on screen gets rewritten.

10

Explain the decisions

A short designer's note closes each project: who it's for, what I chose, what I'd do next.

Case study · E-learning course · Developers

Your First Inference Request

A 20-minute course that takes a Python developer from no API key to a working request to Nebius Token Factory, and teaches them to read and change the response.

Open the courseDownload xAPI package
My roleSole designer: product audit, objectives, content, code testing, visuals, Rise build, tracking
AudiencePython developers making their first call to an LLM API
LengthAbout 20 minutes · 8 lessons · 4 objectives
Design modelMerrill's First Principles and Carroll's minimalism, with Mayer's pre-training
MediaSupademo walkthrough, animated request diagram, tested Python code, knowledge checks
BuildRise 360, xAPI, tested in SCORM Cloud
1 · Analyse 2 · Design 3 · Develop 4 · Implement 5 · Evaluate Key decisions What I'd do next
1 · Analyse

I went through onboarding as a new user

I signed up for Token Factory and followed the official quickstart, noting every place I got stuck. Three findings shaped the course:

  • Too much before the first result. Projects, tenants, IAM and quotas all appear before a developer has sent a single request.
  • Errors aren't explained. The most common first errors have no guidance next to them.
  • The quickstart example fails for new users. Its model, DeepSeek-R1-0528, is only available on a dedicated endpoint (checked in the model catalog, September 2026), so copying the example returns an error on the very first request.

Who the learner is

A backend developer asked to add a language model to a product. Comfortable with Python and the terminal; new to API keys, tokens, temperature and finish_reason. Explaining what a terminal is would sound condescending.

The course is for developers who want to use a model through Token Factory, not run one on Nebius AI Cloud. Lesson 1 says so, and points the second group elsewhere.

2 · Design

Four objectives, four lessons, four quiz questions

ObjectiveThe learner can…Lesson
CreateCreate an API key and keep it in an environment variable, not in the code2
SendSend a chat-completion request to Token Factory from Python4
ReadFind the generated text, why generation stopped, and how many tokens it used5
ChangeChange the model and the temperature, and predict what each change does6

Lesson titles repeat the four verbs, and the final quiz has one question per objective, each in a new situation rather than a repeat of a lesson check.

Why these models

Merrill's First Principles put one real task at the centre: get a first answer from the model. Carroll's minimalism, written for teaching software, says people learn by doing and by recovering from errors, so the course gets to code fast and treats errors as content. Mayer's pre-training sets a hard cap: five new terms before the code, everything else when it's needed.

3 · Develop

Everything checked against the live product

  • Base URL and key variable checked against the official quickstart. An earlier draft used API_KEY, which would have failed.
  • Model chosen from the live catalog: Qwen/Qwen3-30B-A3B-Instruct-2507, marked Public, fast and cheap. An Instruct model rather than a reasoning one, so temperature visibly changes the answer in lesson 6.
  • Code run on my own machine. The response in lesson 5 is the real one: finish_reason: "stop", 60 tokens.
  • The OpenAI key trap. If the Nebius key isn't set, the library complains about OPENAI_API_KEY, and beginners think they need an OpenAI key. The error block in lesson 4 explains this.

Media

A Supademo walkthrough of creating a key in the real console, an animated diagram of the request pipeline, code in Rise code blocks so indentation survives copying, and no narration: developers skim and copy code, and a voice reading on-screen text adds load without adding meaning.

4 · Implement

Built in Rise, tracked with xAPI

Completion is based on the final quiz, pass mark 75%, reported as passed or failed so the LMS shows whether the objectives were met, not just whether the course was scrolled through. Rise doesn't send in-lesson knowledge checks to the LMS, so all metrics are built on the final quiz.

The web version on GitHub Pages runs without an LMS, so anyone can take it. The xAPI package is available to download above.

5 · Evaluate

Tested in an LMS

I uploaded the xAPI package to SCORM Cloud and took the course as a learner, with one deliberate wrong answer:

Reviewed by two engineers

The course was reviewed by Igor Borovik, Python Developer, and Aleksandr Kolesnikov, Modern Workplace Engineer and Infrastructure Team Lead at Nebius. Their comments led to four changes:

  • Lesson 2 now opens by explaining why we use the openai library: it saves writing HTTP requests by hand.
  • Explanations moved into the code itself, as comments next to each line.
  • Lesson 4 explains messages as a chat that the model completes, not a single question.
  • The three roles, system, user and assistant, are explained, with a check on where rules for the whole chat belong.

How I'd measure it in production

In the course: completion, quiz pass rate and the questions failed most. In the product: the share of new accounts that make a first successful API call, and how fast. In support: fewer tickets about keys, base URLs and unavailable models. The product metric matters most, because the course exists to get people using the platform.

Key decisions
First success comes first

Key and request come early. Projects, IAM and quotas wait for a later module, once the learner has a reason to care.

Five terms, hard cap

Only API key, base URL, model ID, token and temperature before the code.

Errors are content

The five most likely first errors sit in the lesson, exactly as the learner sees them.

Nothing copied from the docs unchecked

Model names, URLs and responses come from the live product, which is how the quickstart problem was found.

What I'd do next
  • Watch 3 developers take the course and note where they stop or copy code incorrectly.
  • Confirm model availability with the product team before each update, since the catalog changes.
  • Add a follow-up module: choosing and comparing models, then streaming and function calling.

Case study · Storyboard · Junior developers

Git Commit Message Generator

A storyboard for a 4-minute interactive lesson: juniors learn to use an AI tool that writes commit messages, and to catch what it gets wrong.

Open the storyboard
My roleSole designer: analysis, objective, script, interactions, feedback, Figma frames
AudienceJunior developers, 0–2 years, who already use Git
Length~4 minutes · 6 screens · 2:20 of practice
Design modelMerrill's First Principles, with Mayer's multimedia principles
DeliverableWritten storyboard with key frames, ready to build in Storyline 360
ContextTest assignment for Nebius Academy; the product is fictional, from the brief
1 · Analyse 2 · Design 3 · Develop 4 · Implement 5 · Evaluate Key decisions What I'd do next
1 · Analyse

The problem

Junior developers write commit messages like "fix", "wip" or "stuff". An AI generator can write better ones, but juniors tend to accept whatever it suggests, including the wrong type of change. The risk isn't that they don't use the tool. It's that they trust it without reading.

Who the learner is

A junior developer with up to two years of experience. Makes commits every day, has never been taught a message format, and has never had to find a bug through the project history.

What they need, and what they don't

  • They need: a reason to care, one format (Conventional Commits), and the habit of checking the tool's suggestion.
  • They don't need: Git basics, message bodies and footers, breaking changes, rewriting history or commitlint setup. Each is worth its own lesson, and none is needed to meet the objective.
2 · Design

One objective

After this lesson, a junior developer can generate a commit message with the tool, check it against the Conventional Commits format, and correct it when the tool gets it wrong.

Why Merrill's First Principles

Merrill's principles start from a real problem, then demonstrate, then let the learner apply. That fits a short lesson where motivation has to come first: juniors won't care about a format until they feel what bad messages cost them.

PrincipleScreenWhat the learner does
Problem1 · Find itTries to find the commit that broke payments in a history of "fix" and "wip". Can't. Then finds it in two seconds when the messages are clear.
Demonstration2 · The ruleSees one message split into type, scope and description
Demonstration3 · The toolWatches the tool propose a message, and a developer fix its wrong scope. Sees what the tool can't do.
Application4 · ChoosePicks the best of three generated messages
Application5 · FixFinds the wrong part of a message and corrects it, unaided
Integration6 · Your codeGets a reference card and one habit to take to the next commit

Support fades across screens 4 and 5: recognise → choose → fix. Every screen uses a fresh example, so no answer is shown before it's asked for. Learners act for 140 of the 240 seconds.

3 · Develop

Why a written storyboard

The lesson is narrated, so the script carries most of the meaning, and a script is what a reviewer can check line by line. Every screen uses the same rows in the same order: narration, on screen, learner action, feedback, technical notes. I only mocked up the parts where layout is part of the learning: the commit log, the editor and the message parts.

What's in the storyboard

  • Narration for every screen, written to be heard, not read.
  • The learner action on every screen, and feedback for every option, right or wrong. Wrong answers explain why, not just "incorrect".
  • Four VS Code frames and a "limit card" for the tool demo, designed in Figma on the VS Code Dark+ palette.
  • A reference card at the end, designed to be screenshotted.

Accessibility

Colour is never the only signal: message parts are numbered as well as coloured. Everything works by keyboard. Narration is captioned, and the lesson works with sound off. Code is real text, not images.

4 · Implement

Ready to build

Storyline 360 rather than Rise, because screens 1 and 5 need state changes and a two-step interaction that Rise blocks can't handle cleanly. Estimated build: 6–8 hours plus narration. The VS Code sequence on screen 3 is the only custom animation. The product is named only twice: in the demo and on the last screen.

Questions for the product team

Before building, I'd confirm what I had to assume: where the Generate button really is in VS Code, IntelliJ and the web app; whether the tool offers one draft or several; whether it can learn a project's own scopes; and which links and tracking the last screen should use.

5 · Evaluate

Expert review, already in progress

Alexandr Tsaplin, Software Engineer at Pinely, reviewed the storyboard for technical accuracy and clarity. Two changes came out of it:

  • Screen 1 now sets the scene first. The reviewer didn't immediately understand the situation. Now the narration introduces it ("You're on call this week…") before any commits appear.
  • Screen 2 now maps each part explicitly. Colour alone didn't make clear that "fix" is the type and "(search)" the scope. Numbered parts and a small table fixed it.

A second developer review is in progress, including the answers experts might disagree on, such as whether raising a limit is a feat.

How I'd measure it

First-try accuracy on screen 5, recorded as a SCORM interaction, and install clicks from UTM-tagged links on the last screen. For a four-minute lesson SCORM is enough; xAPI would add setup without adding data we need. If most get screen 5 wrong, screen 3 needs a clearer demonstration of checking.

Key decisions
Open with a failure

The learner can't find the bug in a bad history. The standard arrives as the answer to a problem they just felt.

Show where the tool stops

The demo includes its mistake and a card on what it can't do. Learners trust a tool more when the lesson is honest about its limits.

Practice is the longest part

The hardest screen, fixing a message, is the longest one. The demo is short.

Ask, don't assume

Where the brief didn't say how the tool works, the storyboard lists the question for the product team instead of inventing an answer.

What I'd do next
  • Finish the second developer review and update any disputed answers.
  • Build a clickable prototype of screen 5 and test it with 2–3 junior developers.
  • Build it in Storyline and publish as SCORM, with first-try accuracy on screen 5 recorded as an interaction.

Case study · 5-day course · Professionals

AI Prompting Essentials

A five-day course that takes office professionals from one-line requests to prompts they can reuse at work, and teaches them when not to trust the answer.

Open the course
My roleSole designer: analysis, objectives, scripts, visual system, video and audio, build
AudienceKnowledge workers who use an AI assistant but rewrite most of what it gives them
Length5 days · 30–40 min a day · 45 lessons
Design model4C/ID, with Mayer's multimedia principles and spaced retrieval
Media7 HeyGen videos · 2 ElevenLabs audio lessons · 20+ interactions
BuildInteractive HTML prototype on GitHub Pages; production target Rise 360 + Storyline
1 · Analyse 2 · Design 3 · Develop 4 · Implement 5 · Evaluate Key decisions What I'd do next
1 · Analyse

The problem

People already use AI assistants at work. Sometimes the answer is great; more often it's generic, too long or slightly wrong, and they rewrite it by hand. Nobody taught them how to ask, or how to check.

Learner persona

Anna, 34, project coordinator. Uses an AI assistant a few times a week to draft emails and summarise meeting notes. Has 30 minutes a day for learning, between meetings, sometimes on her phone. Doesn't need the theory behind language models.

Performance gap

TodayAfter the course
One-line requests, then manual rewritingStructured prompts that produce usable first drafts
Accepts or rejects the first answerDiagnoses what's missing and refines
Unsure when the output can be trustedChecks facts, numbers and sources before using it
Pastes whatever is at hand, including sensitive dataKnows what must never go into a prompt

Is training the right answer?

Partly. A job aid can hold the checklist, but the core skill, deciding what the model needs to know for this task, is a judgement that changes every time. That can only be built through practice on varied, whole tasks. So the course is built around practice, with the job aid as support.

Constraints

  • Short sessions, often on mobile → every lesson and interaction works on a phone.
  • Different AI tools across companies → principles that transfer to any assistant.
  • Model outputs change over time → every example is pre-generated, dated and labelled.
2 · Design

Objectives first

Eight observable objectives, written as action, condition and criterion. None starts with "understand". Each one is practised in a task and measured in a check or in the capstone.

DayThe learner can…Bloom
1Spot which of the four elements (task, context, constraints, format) a prompt is missing, in 4 of 5 casesAnalyse
1Rewrite a one-line request into a prompt that produces a usable first draftApply
2Add labelled material (text, file, image) and examples so the output matches a required styleApply
3Diagnose why an answer misses and choose the right fixAnalyse
3Check an answer for invented facts and biased wording before using itEvaluate
4Split a complex task into a chain of prompts and ask for tables and checklistsApply
AllSort information into safe, remove first, never, with no errors on "never"Apply
5Build and test a reusable prompt template for a recurring taskCreate

Why 4C/ID

Prompting looks simple, but it's a judgement skill: there is no single correct prompt. Courses that teach it as a list of tips produce people who can recite the tips and still write weak prompts. 4C/ID was built for complex skills like this. It puts whole, realistic tasks at the centre, orders them from simple to complex, and withdraws support as competence grows.

4C/ID componentIn this course
Learning tasksOne task class per day, from a single clear request to the learner's own recurring task
Supportive informationA short presenter video each day: why the model answers the way it does
Procedural informationPrompt anatomy, the chain pattern, a template: given exactly when needed
Part-task practiceQuick drills: spot the missing element, name the cause, pick the shape, safe to paste

Five task classes, simple to complex

Day 1One clear request
Day 2Working from material
Day 3When the answer is wrong
Day 4Multi-step work
Day 5Your own task

Inside each day, support fades: worked example → completion task → real task in the learner's own AI assistant. The next day starts a harder task class and support goes back up. Days 2–5 open with two retrieval questions on the day before.

3 · Develop

Real outputs only

Every AI answer in the course is real: generated in a clean chat, unedited, and labelled with the model and date. I ran 30+ prompts and built the lessons around what actually came back, including the mistakes. Those mistakes became the best teaching material:

  • The same budget line came back as "$4k" in one run and "€4k" in the next. The notes gave no currency.
  • Asked "why was the launch cancelled?", the model explained a cancellation that never happened.
  • A job ad prompt with "young and energetic" produced an ad that repeated "young".
  • A tested template flagged unclear items in one run and said "nothing is unclear" in another.

The right medium for each job

MediumUsed forWhy
Video · HeyGenOpening each day: the "why"A face and a voice help a mental model land. Seven videos, one presenter: an AI avatar of me, disclosed to learners
Audio · ElevenLabsTwo procedural lessonsOptional, next to the same text. Nothing to show on screen, so a video would add nothing
InteractionsAll practiceFix-the-prompt builder, spot-the-wrong-row, click the sentence that needs fixing, order the chain, drills

All videos follow one style system: a 1920×1080 grid, three layouts (Full, Bubble, Split), fixed card sizes and one palette, documented so any video can be updated without redesign.

Accessibility

Captions in every video and a transcript below it. Every interaction works by keyboard and click. Colour is never the only signal. Plain English for non-native speakers. Tested at phone width.

4 · Implement

From prototype to production

The whole course is built as a working HTML prototype and published on GitHub Pages, so anyone can take it without an account. The production target is Rise 360 with embedded Storyline blocks, reporting completion, quiz score and capstone result to the LMS through xAPI.

Self-paced by design: one day at a time, 30–40 minutes, spaced over a week.

5 · Evaluate

Assessment

  • Every day: drills and checks with feedback on every option, not just "incorrect".
  • Final check: 10 scenario questions drawn from a bank of 20, options shuffled, pass mark 8 of 10.
  • Capstone: the learner builds a template for their own weekly task, tests it on two real cases and checks it against four criteria: complete, reusable, safe, tested.
  • Certificate: of achievement when both are passed, of completion otherwise.

Evaluation plan

Kirkpatrick levelMeasure
1 · ReactionThree-question pulse at the end of each day
2 · LearningFinal check score; capstone criteria
3 · BehaviourSurvey after 30 days: do they still use their template, how much do they rewrite AI output
4 · ResultsAgreed with the stakeholder before launch, e.g. time saved on recurring writing tasks

After the first 100 learners, the data triggers changes: any question fewer than 40% get right is reviewed for ambiguity; any day with more than 20% drop-off is reviewed for length.

Key decisions
Pre-generated, not live AI

A live model inside the course would make feedback impossible to write. Real, dated outputs keep every feedback line true to what the learner sees.

Show the model's mistakes

Every worked example includes something the model got wrong. The course teaches checking by showing why it's needed.

Data safety is non-negotiable

"Safe to paste?" is a daily item and a criterion the capstone can't pass without.

Video only where a face helps

Video opens each day. Procedures are text or optional audio, so learners can follow them at their own pace.

What I'd do next
  • Pilot Day 1 with 3–5 people from the audience, with think-aloud on the "Fix the prompt" task.
  • SME review of all examples by someone who uses AI assistants daily.
  • Rebuild in Rise 360 + Storyline and test xAPI statements in SCORM Cloud.
  • Add Supademo walkthroughs for tool-specific steps: new chat, attaching a file.
